# Backend API extensions

GET `/api/users` returns `{users:[{id,username,role,active}]}`. POST `/api/users` accepts `{username,password,role}`. PUT `/api/users/:id` accepts `{username,role,active,password?}`; passwords must contain 12–256 characters. A role, password, or active status change invalidates that user's sessions, and at least one active admin is required. PUT `/api/classes/:id` accepts `{name}`. GET `/api/assignments` returns `{assignments:[{userId,classId,username,className}]}`. POST and DELETE `/api/assignments` accept `{userId,classId}`. These operations require an admin.

PUT `/api/students/:id` accepts the documented student fields and optional boolean `active`. A transfer to another class starts at `startDate` and ends the most recent previous enrollment the day before, unless that enrollment already ended earlier. A return to a prior class creates another interval, which is combined into a single student report. Overlaps and changes that would invalidate records are rejected. Deactivation preserves historical marks; enrollment dates, rather than the active flag, determine eligibility in daily screens and reports. Set an end date to end eligibility. Roll numbers remain reserved within the class for historical stability.

GET `/api/audit?classId=...&date=YYYY-MM-DD` returns `{audit:[{studentId,period,previous,value,reason,actor,timestamp}]}` for authorized class users. Audit timestamps are UTC ISO strings.

GET `/api/reports` and `/api/reports.csv` accept optional `studentId` in addition to `classId` and `month`. The same calculation filters to that student for either format; a student without enrollment in that class and month returns 404.

Initial unmarked periods have no stored row; explicitly clearing a saved value stores `U` and is audited. Later changes to that saved `U` also require a reason. PUT attendance may submit a subset of eligible entries; a successful submission advances the class/date version. Daily statuses include keys for all seven periods; `periods` specifies which controls are eligible.

Sessions are held server-side in process memory and expire after eight hours, so users must sign in again after restart. Obtain a CSRF token before login and again after login (the login response also contains the rotated token). Login verifies against a dummy hash for unknown usernames so timing does not reveal account existence, and ten failures for one client/username in fifteen minutes return 429. The server normalises API paths before its `/api/` CSRF check, so case-variant paths cannot bypass it, and sets nosniff, frame-deny, no-referrer and a self-only CSP headers; API responses are no-store. It binds `0.0.0.0` so containers and port-forwards work, so run the demo on an isolated host. Set `COOKIE_SECURE=true` when serving over HTTPS. SQLite data lives at `DB_PATH` (default `data/attendance.sqlite`); the schema is applied idempotently on opening. Admin bootstrap is `ADMIN_USERNAME` plus an `ADMIN_PASSWORD` of at least 12 characters for `node scripts/seed.js`. Set `SEED_DEMO=true` to add clearly named synthetic records.
